## 0. Назначение документа

Этот документ описывает, какую документацию готовит **Domain Expert** для каждого домена и каждого trainer product.

Domain Expert — это специалист предметной области, который отвечает за профессиональную точность тренажера.

Примеры:

```text
Medicine → врач / клинический преподаватель
QA → QA Lead / Senior QA Engineer
Sales → Sales Lead / Head of Sales
Cybersecurity → Security Specialist
English → преподаватель английского / методист
Legal → юрист
Finance → финансовый специалист / compliance expert
```

Главная задача Domain Expert:

```text
Сделать так, чтобы тренажер был профессионально корректным, реалистичным, безопасным и полезным.
```

---

## 1. Роль Domain Expert в проекте

Domain Expert не проектирует всю платформу и не отвечает за UX или backend.

Он отвечает за:

```text
профессиональную корректность
реалистичность ситуаций
термины
типовые ошибки
уровни сложности
критичные ошибки
корректность рубрик
безопасность рекомендаций
валидацию сценариев
валидацию AI feedback
```

Он работает вместе с:

```text
Product Owner
Business Analyst
Product Manager
Learning Experience Designer
AI Architect
QA Lead
UX/UI Designer
```

---

## 2. Главный принцип доменной экспертизы

Тренажер не должен выглядеть как “AI придумал вопросы по теме”.

Он должен отражать реальные профессиональные ситуации.

Правильная формула:

```text
реальная профессиональная ситуация
→ типичное действие специалиста
→ типичные ошибки новичка
→ критерии хорошего выполнения
→ critical errors
→ безопасный feedback
```

Неправильная формула:

```text
общие вопросы из интернета
→ общая AI-оценка
→ generic advice
```


### 7.2. Glossary Template

| Term | Definition | Common confusion | Example | Locale notes |
|---|---|---|---|---|

### 7.3. QA Glossary Example

| Term | Definition | Common confusion | Example |
|---|---|---|---|
| Bug | Несоответствие фактического поведения ожидаемому | Bug vs feature request | Кнопка Save не сохраняет данные |
| Bug report | Документ/запись с описанием дефекта | Путают с простым сообщением “не работает” | Title, steps, actual, expected |
| Severity | Влияние дефекта на систему/пользователя | Путают с priority | Payment не работает — high severity |
| Priority | Срочность исправления | Путают с severity | Minor UI bug перед релизом может быть high priority |
| Regression testing | Проверка, что новые изменения не сломали старый функционал | Путают с retest | После новой версии проверяем старые функции |
| Retest | Повторная проверка исправленного бага | Путают с regression | Баг исправили — проверяем именно его |
| Smoke testing | Быстрая проверка, что основное работает | Путают с sanity | Приложение запускается, login работает |
| Test case | Подробный тестовый сценарий с шагами и expected result | Путают с checklist | Step 1, Step 2, Expected |
| Checklist | Список проверок без детальных шагов | Путают с test case | Проверить login, logout, password reset |
| API request | Запрос к API | Путают с UI-действием | GET /users |
| HTTP status code | Код результата HTTP-запроса | Путают смысл 400/401/403/500 | 404 — not found |

## 10. Critical Errors Catalog

### 10.1. Назначение

Critical Error — ошибка, которая блокирует PASS, даже если часть ответа хорошая.

### 10.2. General Rule

```text
Если ответ содержит critical error, сценарий не может быть отмечен как passed.
```

### 10.3. Critical Error Template

| Error ID | Critical Error | Blocks Pass | Reason | Safe Feedback |
|---|---|---|---|---|

### 10.4. QA Critical Errors

| Error ID | Critical Error | Blocks Pass | Reason |
|---|---|---|---|
| QA-CRIT-001 | Пользователь говорит, что steps to reproduce в bug report не нужны | Yes | Без шагов баг часто невозможно проверить |
| QA-CRIT-002 | Пользователь полностью не понимает роль QA | Yes | Базовое несоответствие роли |
| QA-CRIT-003 | Пользователь утверждает, что тестировать нужно только happy path | Yes | Игнорирует негативные и edge cases |
| QA-CRIT-004 | Пользователь путает actual и expected result до противоположного смысла | Yes | Невозможно корректно оформить дефект |
| QA-CRIT-005 | Пользователь предлагает скрывать баги от команды/клиента | Yes | Нарушение профессиональной этики |
| QA-CRIT-006 | Пользователь выдумывает опыт и советует так делать | Yes | Опасная профессиональная рекомендация |
| QA-CRIT-007 | Пользователь говорит, что QA не нужно читать требования | Yes | Нарушение базовой QA-логики |
| QA-CRIT-008 | Пользователь предлагает тестировать production без разрешения | Yes | Риск безопасности и данных |

### 10.5. Safe Feedback Example for Critical Error

```text
В ответе есть критичная ошибка: вы указали, что steps to reproduce не нужны.
Для QA это важная часть bug report, потому что без нее разработчику сложно повторить проблему и проверить исправление.

Следующий шаг:
повторите ответ по структуре:
title → steps to reproduce → expected result → actual result → environment.
```

## 16. Rubric Validation

### 16.1. Назначение

Domain Expert проверяет не только сценарии, но и критерии оценки.

Rubric Validation отвечает на вопросы:

```text
критерии профессионально корректны?
уровни score описаны адекватно?
critical errors действительно критичные?
feedback не содержит опасных советов?
AI не завышает/не занижает оценку?
```

### 16.2. Rubric Validation Checklist

| Check | Required |
|---|---|
| Criteria match real professional skill | Yes |
| Criteria are measurable | Yes |

## 19. Safety Review

### 19.1. Why Safety Review Exists

Some domains can create harm if the trainer gives wrong or unsafe guidance.

High-risk domains:

```text
medicine
legal
cybersecurity
finance
mental health
child education/safety
```

For these domains, Domain Expert review is mandatory before publication.

### 19.2. Domain Risk Levels

| Domain | Risk Level | Expert Review Required |
|---|---:|---|
| IT interview | Low/Medium | Recommended |
| Sales | Medium | Recommended |
| English | Low/Medium | Recommended |
| Cybersecurity | High | Mandatory |
| Medicine | High | Mandatory |
| Legal | High | Mandatory |
| Finance | High | Mandatory |

### 19.3. Safety Review Checklist

```text
No dangerous advice
No illegal instructions
No unsafe medical/legal/financial claims
No diagnosis/treatment without disclaimer and expert protocol
No security offensive instructions unless controlled and ethical
No discrimination
No privacy violations
No encouragement to fake experience or credentials
```

---

## 20. Medicine Safety Rules

Medicine trainer cannot be published unless:

```text
licensed medical expert reviewed scenarios
medical disclaimers exist
patient safety rules exist
red flags are handled carefully
AI does not replace clinician
no unsafe dosage/procedure instructions without controlled educational context
emergency guidance is safe and conservative
```

Example forbidden behavior:

```text
AI gives diagnosis as final truth.
AI tells user to ignore red flags.
AI recommends medication dosage without context.
```

---

## 21. Legal Safety Rules

Legal trainer cannot be published unless:

```text
qualified legal expert reviewed content
jurisdiction is explicit
disclaimers exist
AI does not present advice as binding legal counsel
high-risk legal decisions are escalated to human expert
```

## 22. Cybersecurity Safety Rules

Cybersecurity trainer cannot be published unless:

```text
security expert reviewed content
scenarios focus on defense/awareness unless explicitly authorized
no malicious operational instructions
phishing examples are controlled
credential theft instructions are forbidden
```

## 23. Finance Safety Rules

Finance trainer cannot be published unless:

```text
finance/compliance expert reviewed content
no personalized investment advice without constraints
risk disclaimers exist
regulatory context is clear
```

## 36. Final Notes

Главная защита проекта на уровне Domain Expert:

```text
Не публиковать тренажер, если его предметная логика не проверена экспертом.
Не считать сценарий хорошим только потому, что AI написал его красиво.
Не считать feedback безопасным, если он не прошел доменную проверку.
Не допускать high-risk домены без отдельного экспертного safety review.
```

Правильный доменный экспертный процесс:

```text
Knowledge Pack
→ Scenario Pack
→ Rubric Validation
→ Safety Review
→ Expert Decision
→ Publication Gate
```
