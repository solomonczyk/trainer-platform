## 1. Исходная продуктовая рамка от Product Owner

### 1.1. Базовая продуктовая модель

Система должна быть не одной большой “мега-машиной” с разделами, а платформой для создания, публикации и прохождения **самодостаточных trainer products**.

```text
Platform
└── Domain
    └── Trainer Product
        └── Trainer Version
            └── Track
                └── Module
                    └── Scenario
                        └── Attempt
                            └── Evaluation
```

### 1.2. Ключевое определение

```text
Платформа = общая инфраструктура.
Домен = большая профессиональная область.
Trainer Product = самостоятельный тренажер внутри домена.
Сценарий = конкретная профессиональная ситуация.
Попытка = один проход сценария пользователем.
Оценка = результат попытки по фиксированной рубрике.
Прогресс = накопленная динамика пользователя внутри конкретного тренажера.
```

### 1.3. Product Owner решения, которые BA не должен искажать

```text
1. Мы строим platform for self-contained trainer products.
2. Мы не строим один mega-trainer.
3. Каждый trainer product имеет собственные сценарии, рубрики, skill map, прогресс и версии.
4. MVP доказывает платформенную модель на одном trainer product.
5. Первый рекомендуемый trainer product: IT → QA Engineer Interview Trainer.
6. MVP text-only; voice mode — later.
7. Progress persistence обязателен с MVP.
8. AI evaluation должна быть rubric-based и evidence-based.
9. High-risk domains требуют expert review.
10. Localization реализуется через locale packs, а не простой перевод.
```

Мы создаем платформу, на которой можно создавать и проходить самодостаточные профессиональные тренажеры.

Платформа должна дать пользователю возможность безопасно тренироваться в реалистичных профессиональных сценариях, получать оценку по рубрике, видеть слабые места, повторять попытки и отслеживать прогресс внутри конкретного тренажера.

```text
Domain: IT
Trainer Product: QA Engineer Interview Trainer
Primary user: Junior / Middle QA Engineer candidate
Mode: text-only
Locales: ru-RU, en-US
```

## 4. Business Problem

### 4.1. Problem statement

Классические курсы и LMS часто дают пользователю теорию, но не дают достаточной практики в реалистичных профессиональных ситуациях. Обычный AI-чат может имитировать собеседование или роль, но не обеспечивает стабильные сценарии, фиксированные рубрики, сохранение прогресса, сравнение попыток, управление версиями и контроль качества.

В результате пользователь не понимает:

- готов ли он к реальной ситуации;
- какие навыки у него слабые;
- как его ответ оценивается по критериям;
- стал ли он лучше после повторных попыток;
- чем конкретно нужно заниматься дальше.

### 4.2. Opportunity

Создать платформу, которая закрывает разрыв между знанием и практическим применением:

```text
knowledge → scenario → user action → rubric evaluation → feedback → retry → progress
```

### 4.3. First market opportunity

Первый trainer product — QA Engineer Interview Trainer — закрывает понятную потребность кандидатов: подготовка к собеседованию по QA через реалистичные вопросы, структурированную оценку и рекомендации.

## 9. Business Processes

### 9.1. User onboarding process

```text
1. User opens platform.
2. User selects language or system detects default locale.
3. User views domain/trainer catalog.
4. User opens trainer product page.
5. User registers or logs in.
6. User enrolls in trainer product.
7. System creates user_trainer_enrollment.
8. User sees available scenarios.
9. User starts first scenario.
```

### 9.2. Scenario attempt process

```text
1. User selects scenario.
2. System creates simulation_session.
3. System loads trainer version, scenario, rubric and locale pack.
4. AI / scenario runtime starts guided interaction.
5. User submits answer(s).
6. System stores transcript.
7. User completes scenario.
8. System creates attempt.
9. Evaluation engine evaluates attempt using rubric.
10. System stores evaluation.
11. System updates trainer progress.
12. User sees score, criteria, evidence, errors and recommendations.
```

### 9.3. Retry process

```text
1. User sees weak points.
2. User starts retry for same scenario.
3. System creates new attempt linked to previous attempt.
4. User completes scenario again.
5. System evaluates new attempt.
6. System compares attempt scores.
7. User sees improvement or degradation.
```

### 9.4. Trainer publication process — MVP seed mode

```text
1. Admin prepares trainer seed package.
2. System validates required trainer fields.
3. System validates scenarios, rubrics and locale packs.
4. Admin publishes trainer as MVP seed data.
5. Trainer appears in catalog.
```

### 9.5. Future trainer publication process — review mode

```text
1. Trainer Author creates draft trainer.
2. Learning Designer reviews training structure.
3. Domain Expert reviews subject correctness.
4. AI Reviewer tests evaluation quality.
5. QA validates trainer package.
6. Product Owner approves publication.
7. Trainer is published as versioned trainer product.
```

## 11. MVP Scope

### 11.1. In scope

```text
1. User registration/login.
2. Basic user profile.
3. Domain catalog with one domain: IT.
4. One trainer product: QA Engineer Interview Trainer.
5. Trainer product page.
6. User enrollment into trainer.
7. 5–10 MVP scenarios.
8. Text-only scenario runtime.
9. Attempt persistence.
10. AI evaluation by rubric.
11. Evaluation result page.
12. Progress page per trainer.
13. ru-RU and en-US locale support.
14. Basic analytics events.
15. Admin seed data for trainer/scenarios/rubrics.
16. Error handling for invalid AI responses.
17. Tests for main flows.
```

### 11.2. Out of scope

```text
1. Voice mode.
2. VR/AR.
3. B2B dashboards.
4. Organization/team management.
5. Marketplace.
6. Full authoring studio.
7. Full billing integration.
8. Multiple domains in production.
9. Multiple trainer products in production.
10. Medical/legal/financial trainers.
11. Automatic trainer generation without review.
12. Certificates with legal/official meaning.
13. SSO.
14. Enterprise security policies.
```

### 11.3. MVP assumptions

```text
1. First trainer content is seed-based, not created through full authoring UI.
2. AI provider can be abstracted later, but MVP must not hardcode business logic directly into one provider response format.
3. Text-only mode is enough to validate scenario/evaluation/progress value.
4. User progress persistence is mandatory.
5. ru-RU and en-US are enough for MVP localization proof.
```

## 35. Trainer Product Rules

```text
BRULE-TP-001: Trainer Product is a commercial/product-level entity, not just a content category.
BRULE-TP-002: Trainer Product must have name, domain, target audience, supported locales, skill map, rubric pack, scenario pack and version.
BRULE-TP-003: Trainer Product can have status: draft, internal_review, expert_review_required, ready_for_test, published, monitored, deprecated, archived.
BRULE-TP-004: Only published trainer products can be enrolled by normal users.
BRULE-TP-005: Deprecated trainer products are hidden from new enrollments but remain available for historical progress.
BRULE-TP-006: Archived trainer products are not executable but historical attempts remain accessible.
```

## 36. Trainer Version Rules

```text
BRULE-TV-001: Every scenario execution must reference trainer_version.
BRULE-TV-002: Updating trainer content must create a new version or controlled revision.
BRULE-TV-003: User attempt history must preserve original trainer version.
BRULE-TV-004: Evaluation must use rubric version active at attempt time.
BRULE-TV-005: User progress may aggregate across versions only if migration rules exist.
```

## 37. Scenario Rules

```text
BRULE-SC-001: Scenario must have objective, context, user role, simulator role, completion condition and rubric reference.
BRULE-SC-002: Scenario must not run without rubric.
BRULE-SC-003: Scenario must not run without supported locale or fallback locale.
BRULE-SC-004: Scenario can have difficulty level.
BRULE-SC-005: Scenario can be retryable unless explicitly disabled.
BRULE-SC-006: Scenario may have critical errors that can cap or fail evaluation.
```

---

## 38. Attempt Rules

```text
BRULE-AT-001: One attempt represents one completed or interrupted scenario run.
BRULE-AT-002: Attempt status can be: started, completed, evaluation_pending, evaluated, evaluation_failed, abandoned.
BRULE-AT-003: Attempt transcript must be preserved for evaluation and user review.
BRULE-AT-004: Abandoned attempts may be shown separately from completed attempts.
BRULE-AT-005: Retry creates a new attempt, not overwriting previous attempt.
```

## 39. Evaluation Rules

BRULE-EV-001: Evaluation must be structured.
BRULE-EV-002: Evaluation must include score per criterion.
BRULE-EV-003: Evaluation must include evidence or controlled evidence_missing reason.
BRULE-EV-004: Evaluation must include weak points.
BRULE-EV-005: Evaluation must include recommendations.
BRULE-EV-006: Invalid AI output cannot be shown as final evaluation.
BRULE-EV-007: Critical errors may override pass status.

BRULE-PR-002: Progress must not be global across unrelated trainers.

## 55. Final Business Analyst Statement

Как Business Analyst, я фиксирую, что система должна решать не задачу “показать пользователю разделы с тренажерами”, а задачу создания и прохождения самодостаточных trainer products, каждый из которых имеет собственную цель, аудиторию, сценарии, рубрики, версии, прогресс и правила оценки.

MVP должен доказать минимальную бизнес-ценность и платформенную модель на одном trainer product: **QA Engineer Interview Trainer** в домене IT.

Ключевые бизнес-требования MVP:

```text
1. Пользователь должен иметь аккаунт.
2. Пользователь должен enroll в trainer product.
3. Пользователь должен пройти сценарий.
4. Система должна сохранить попытку.
5. Система должна оценить попытку по рубрике.
6. Пользователь должен увидеть score, evidence, weak points and recommendations.
7. Система должна сохранить прогресс отдельно по этому trainer product.
8. Система должна поддерживать ru/en локализацию.
9. Система должна собирать analytics events.
10. Система не должна превращаться в mega-trainer.
```

Этот документ готов к передаче Product Manager, Architect, UX/UI Designer, Learning Designer, AI Architect и QA Lead для следующего уровня детализации.
