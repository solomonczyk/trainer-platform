## 0. Назначение документа

Этот документ описывает, какие данные, события, метрики и аналитические панели нужны платформе с первого MVP.

Data / Analytics Specialist нужен с самого начала, потому что без аналитики невозможно понять:

- работает ли продукт;
- проходит ли пользователь путь до первой ценности;
- какие тренажеры полезны;
- где пользователи бросают сценарии;
- улучшаются ли навыки;
- насколько AI-оценка стабильна;
- сколько стоит одна AI-оценка;
- есть ли смысл в монетизации;
- какие сценарии нужно улучшать.

Главный принцип:

```text
Если мы не измеряем прохождение, прогресс, повторные попытки, AI cost и retention — мы не управляем продуктом.
```

## 2. Analytics Principles

### 2.1. Events from Day One

MVP должен собирать события с первого дня.

Не позже.

### 2.2. One Event = One Meaning

Событие не должно означать несколько вещей.

Плохо:

```text
user_action
```

Хорошо:

```text
scenario_started
answer_submitted
evaluation_received
retry_started
```

### 2.3. Trainer Context Required

Почти все события должны содержать:

```text
domain_slug
trainer_product_id
trainer_slug
trainer_version
scenario_id
locale
user_id or anonymous_id
```

Иначе нельзя анализировать по отдельным trainer products.

### 2.4. Progress is per Trainer

Аналитика прогресса должна считаться отдельно:

```text
QA Trainer progress ≠ Sales Trainer progress ≠ English Trainer progress
```

### 2.5. AI Cost is Product Metric

AI cost — не техническая деталь, а бизнес-метрика.

## 7. Metrics Dictionary

## 7.1. Activation Metrics

### activation_rate

```text
Definition:
registered users who received first evaluation / registered users

Formula:
activation_rate = users_with_first_evaluation / registered_users

Segment by:
locale, trainer_slug, acquisition_source
```

### first_evaluation_completion_rate

```text
Definition:
users who started first scenario and received evaluation / users who started first scenario

Formula:
first_evaluation_completion_rate = first_evaluation_received / first_scenario_started
```

### time_to_first_evaluation

```text
Definition:
Time between registration and first evaluation_received.
```

---

## 7.2. Engagement Metrics

### scenario_start_rate

```text
Definition:
users who started scenario / users who viewed trainer product
```

### completion_rate

```text
Definition:
completed evaluated scenarios / started scenarios

Formula:
completion_rate = scenario_completed / scenario_started
```

### repeat_attempt_rate

```text
Definition:
users who started retry / users who received evaluation

Formula:
repeat_attempt_rate = retry_started_users / evaluated_users
```

### hint_usage_rate

```text
Definition:
attempts with hint_requested / total attempts
```

---

## 7.3. Learning Metrics

### score_improvement

```text
Definition:
Score delta between previous attempt and retry for same user/scenario.

Formula:
score_improvement = retry_score - previous_score
```

### skill_score_improvement

```text
Definition:
Change in skill score over time per trainer product.
```

### critical_error_rate

```text
Definition:
attempts with at least one critical error / evaluated attempts
```

### readiness_distribution

```text
Definition:
Distribution of users by readiness status:
not_started, in_progress, needs_practice, almost_ready, ready, strong
```

### retry_improvement_rate

```text
Definition:
retries with improved score / total retries
```

---

## 7.4. Retention Metrics

### D1 retention

```text
Definition:
users active 1 day after registration / registered users
```

### D7 retention

```text
Definition:
users active 7 days after registration / registered users
```

### D30 retention

```text
Definition:
users active 30 days after registration / registered users
```

### trainer_return_rate

```text
Definition:
users who return to same trainer within 7 days / users enrolled in trainer
```

## 7.5. Monetization Metrics

### free_to_paid_conversion

```text
Definition:
users who become paid / free users exposed to paid offer
```

### payment_conversion_rate

## 9. Data Quality Rules

### 9.1. Event Quality

Each event must have:

```text
event_id
event_name
occurred_at
source
user_id or anonymous_id
```

For trainer-related events:

```text
trainer_slug
trainer_version
domain_slug
locale
```

For scenario-related events:

```text
scenario_id
attempt_id when applicable
```

### 9.2. Forbidden Event Practices

```text
do not send raw user answer in analytics event properties
do not send email/payment secrets in event properties
do not duplicate events without idempotency
do not use vague event names
do not change event meaning without versioning
```

### 9.3. Event Versioning

If event schema changes significantly:

```text
event_schema_version must be updated
```

## 14. SQL View Examples

### 14.1. Funnel View

```sql
CREATE VIEW analytics_funnel_daily AS
SELECT
  date_trunc('day', occurred_at) AS day,
  count(*) FILTER (WHERE event_name = 'landing_viewed') AS landing_viewed,
  count(*) FILTER (WHERE event_name = 'user_registered') AS user_registered,
  count(*) FILTER (WHERE event_name = 'trainer_viewed') AS trainer_viewed,
  count(*) FILTER (WHERE event_name = 'trainer_enrolled') AS trainer_enrolled,
  count(*) FILTER (WHERE event_name = 'scenario_started') AS scenario_started,
  count(*) FILTER (WHERE event_name = 'answer_submitted') AS answer_submitted,
  count(*) FILTER (WHERE event_name = 'evaluation_received') AS evaluation_received
FROM analytics_events
GROUP BY 1;
```

### 14.2. AI Cost by Trainer

```sql
CREATE VIEW ai_cost_by_trainer_daily AS
SELECT
  date_trunc('day', created_at) AS day,
  trainer_slug,
  count(*) AS ai_requests,
  sum(estimated_cost_usd) AS total_cost_usd,
  avg(latency_ms) AS avg_latency_ms
FROM ai_requests
WHERE status = 'success'
GROUP BY 1, 2;
```

### 14.3. Scenario Completion

```sql
CREATE VIEW scenario_completion_daily AS
SELECT
  date_trunc('day', occurred_at) AS day,
  trainer_slug,
  scenario_id,
  count(*) FILTER (WHERE event_name = 'scenario_started') AS started,
  count(*) FILTER (WHERE event_name = 'scenario_completed') AS completed
FROM analytics_events
GROUP BY 1, 2, 3;
```

## 25. Final Notes

Главная аналитическая защита проекта:

```text
Не считать прохождение ценностью, пока пользователь не получил evaluation.
Не считать trainer product успешным, пока нет повторных попыток и улучшения score.
Не считать AI-слой рабочим, пока не измеряется cost, latency и failure rate.
Не считать аналитику безопасной, если в event properties попадают raw answers.
```

Правильный MVP analytics proof:

```text
user_registered
→ trainer_viewed
→ trainer_enrolled
→ scenario_started
→ answer_submitted
→ evaluation_received
→ scenario_completed
→ progress_viewed

и при этом:
AI cost logged
raw answer not stored in analytics events
trainer context present
metrics calculable
```
