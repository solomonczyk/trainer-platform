Этот документ фиксирует позицию Product Manager по продукту: **что делать первым, вторым и третьим**, какие функции входят в MVP, какие фичи откладываются, какие пользовательские сценарии являются ключевыми, какие метрики определяют успех, какие зависимости нужно учитывать и как должен выглядеть релизный план.

## 1. Product Management Summary

### 1.1. Базовое продуктовое решение

Мы создаем не один большой тренажер и не LMS, а платформу для создания, публикации и прохождения **самодостаточных trainer products**.

```text
Platform
└── Domain
    └── Trainer Product
        └── Trainer Version
            └── Track
                └── Module
                    └── Scenario
                        └── Attempt
                            └── Evaluation
```

### 1.2. Первый MVP

Первый MVP должен доказать, что платформа умеет:

```text
1. Хранить trainer product как самостоятельный продукт.
2. Показывать trainer product пользователю.
3. Давать пользователю enroll / начать прохождение.
4. Запускать scenario внутри trainer product.
5. Сохранять attempt.
6. Выполнять AI evaluation по rubric.
7. Показывать score, feedback, weak points и next recommendation.
8. Сохранять progress отдельно по trainer product.
9. Работать минимум на ru-RU и en-US.
10. Собирать базовые analytics events.
```

### 1.3. Первый trainer product

```text
Domain: IT
Trainer Product: QA Engineer Interview Trainer
Primary user: Junior / Middle QA Engineer candidate
Mode: text-only
Locales: ru-RU, en-US
```

### 1.4. Главный продуктовый принцип

```text
MVP должен доказать платформенную модель через один самодостаточный trainer product, а не пытаться сразу покрыть много доменов и профессий.
```

## 2. PRD Overview

### 2.1. Product Name

Рабочее название:

```text
Trainer Platform
```

Первый trainer product:

```text
QA Engineer Interview Trainer
```

### 2.2. Product Type

```text
AI-powered simulation platform for self-contained professional trainers
```

### 2.3. MVP Product Type

```text
Text-based AI interview simulation trainer with rubric-based evaluation and progress tracking
```

### 2.4. Problem Statement

Пользователи, которые готовятся к профессиональным собеседованиям, часто изучают теорию, смотрят видео или читают материалы, но не имеют безопасной среды для практики реального интервью.

Обычный AI-чат может задавать вопросы, но не дает устойчивой структуры:

- нет фиксированных сценариев;
- нет стабильной рубрики оценки;
- нет сохранения попыток;
- нет прогресса по навыкам;
- нет версии тренажера;
- нет локализованного контекста;
- нет контроля качества контента.

### 2.5. Product Goal

Создать платформу, на которой пользователь может пройти самостоятельный профессиональный тренажер, получить оценку по рубрике, увидеть слабые места и повторять практику с сохранением прогресса.

### 2.6. MVP Goal

Создать первый работающий vertical slice:

```text
Platform Core + QA Engineer Interview Trainer + text simulation + rubric evaluation + progress + ru/en localization + basic analytics
```

## 4. Product Scope

### 4.1. MVP In Scope

```text
1. User registration / login или упрощенный auth flow.

4. Trainer product page.
5. QA Engineer Interview Trainer as first trainer product.
6. Trainer enrollment.
7. Scenario list.
8. Scenario runtime.
9. Text-based answer submission.
10. Attempt persistence.
11. AI rubric-based evaluation.
12. Evaluation result screen.
13. Progress per trainer product.
14. Basic dashboard / profile progress.
15. ru-RU and en-US localization foundation.
16. Analytics events.
17. Admin seed data mechanism.
18. Tests.
19. Proof JSON.
```

### 4.2. MVP Out of Scope

```text
1. Voice mode.
2. Video mode.
3. VR / AR.
4. Marketplace.
5. Full authoring studio.
6. B2B organization dashboard.
7. Team management.
8. Payments production integration.
```

```text
1. Trainer product must be self-contained.
2. Progress must be saved per trainer product.
3. AI evaluation must be rubric-based.
4. AI evaluation must return structured result.
5. User must see feedback and next recommendation.
6. MVP must not become one universal free AI chat.
7. Platform must support future trainer products by design.
8. Basic analytics must exist from MVP.
```

## 5. MVP Functional Requirements

## 5.1. FR-001 — User Account

### Description

Пользователь должен иметь возможность войти в систему, чтобы его попытки, оценки и прогресс сохранялись.

### MVP behavior

```text
- Пользователь может зарегистрироваться или войти.
- Пользователь имеет уникальный profile.
- Система связывает attempts и progress с пользователем.
```

### Priority

```text
P0 — Must Have
```

---

## 5.2. FR-002 — Domain Catalog

### Description

Платформа должна поддерживать домены как большие профессиональные области.

### MVP behavior

```text
- В MVP доступен минимум один domain: IT.
- Domain используется для группировки trainer products.
- Domain не является тренажером сам по себе.
```

### Priority

```text
P1 — Should Have for platform proof
```

---

## 5.3. FR-003 — Trainer Product Page

### Description

Каждый trainer product должен иметь собственную страницу, которая объясняет его цель, аудиторию, сценарии, языки и ожидаемый результат.

### MVP behavior

```text
- Пользователь видит страницу QA Engineer Interview Trainer.
- На странице указано, для кого тренажер.
- Пользователь видит список доступных сценариев.
- Пользователь может начать тренажер.
```

### Priority

```text
P0 — Must Have
```

---

## 5.4. FR-004 — Trainer Enrollment

### Description

Пользователь должен быть enrolled в конкретный trainer product, чтобы прогресс считался отдельно.

### MVP behavior

```text
- Пользователь нажимает “Начать тренажер”.
- Создается или активируется enrollment.
- Progress хранится внутри enrollment.
```

### Priority

```text
P0 — Must Have
```

### Priority

## 5.6. FR-006 — Scenario Runtime

### Description

Система должна запускать сценарий как контролируемую симуляцию, а не как свободный чат без границ.

### MVP behavior

```text
- Пользователь открывает scenario.
- Система показывает контекст и вопрос.
- Пользователь отправляет текстовый ответ.
- Система сохраняет transcript.
- Система завершает attempt и отправляет его на evaluation.
```

### Priority

```text
P0 — Must Have
```

### Description

Каждая попытка прохождения scenario должна сохраняться.

### MVP behavior

```text

- user answer сохраняется.
- scenario version сохраняется.
- locale сохраняется.
- evaluation привязывается к attempt.
```

### Priority

```text
P0 — Must Have
```

### Description

AI должен оценивать ответ пользователя по фиксированной рубрике.

### MVP behavior

```text

passed
criteria_scores
evidence
weak_points
critical_errors
recommendations
next_scenario_recommendation
```

### Priority

```text
P0 — Must Have
```

```text

- Что получилось хорошо.
```


# PART F. MVP Definition

---

## 32. MVP Definition

### 32.1. MVP Statement

MVP — это первая версия платформы, которая доказывает, что один самодостаточный trainer product может быть создан, опубликован, пройден пользователем, оценен AI по рубрике, сохранен в прогрессе и измерен аналитикой.

### 32.2. MVP Includes

```text
Platform core
One domain: IT
One trainer product: QA Engineer Interview Trainer
One trainer version: v1
Minimum 5 scenarios
Minimum 1 final mixed scenario
ru-RU and en-US content foundation
Text-only scenario runtime
AI evaluation
Progress dashboard
Basic analytics
Seed data
Tests
```

### 32.3. MVP Does Not Include

```text
Voice
Video
Marketplace
B2B dashboard
Payments production
Full authoring studio
Medical/legal trainers
External expert publishing
Native apps
Official certification
```

---

## 33. MVP Success Criteria

### 33.1. Product Success

```text
1. User completes first scenario.
2. User receives understandable evaluation.
3. User understands weak points.
4. User can retry scenario.
5. Progress updates after attempt.
6. User can return later and see previous progress.
```

### 33.2. Business Success

```text
1. First 100 users can be onboarded without manual intervention.
2. >= 60% of started scenarios reach evaluation result.
3. >= 25% users start second attempt or second scenario.
4. >= 40% users understand their weak points according to feedback survey.
5. Cost per completed evaluated simulation is measurable.
```

### 33.3. Technical/Product Quality Success

```text
1. Evaluation JSON is valid in >= 95% cases.
2. Critical evaluation errors <= 5% in test set.
3. Core funnel analytics events captured.
4. No data loss for attempts/progress.
5. Tests pass.
```

---

## 34. MVP Failure Criteria

MVP считается продуктово слабым, если:

```text
1. Users complete one scenario but do not retry.
2. Users do not understand why they received a score.
3. Feedback feels generic and not better than normal ChatGPT.
4. Evaluation is inconsistent or unfair.
5. Progress screen does not motivate continuation.
6. AI cost per completed evaluation is too high for planned pricing.
7. The first trainer cannot be extended into another trainer without redesign.
```

# 52. Final Product Manager Conclusion

Product Manager позиция по проекту:

```text
Мы не строим сразу огромную платформу со всеми возможными тренажерами.
Мы строим платформенное ядро и доказываем его через один самодостаточный trainer product.
Первый trainer product — QA Engineer Interview Trainer.
MVP должен быть достаточно узким для реализации, но достаточно архитектурно правильным, чтобы позже добавить другие trainer products без переписывания ядра.
```

Финальное PM-решение:

```text
Phase 1 должен дать работающий продуктовый цикл:
Пользователь → trainer product → scenario → answer → evaluation → progress → retry.
```

Если этот цикл работает, платформа имеет продуктовую основу для дальнейшего расширения.
