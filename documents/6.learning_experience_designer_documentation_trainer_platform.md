## 0. Назначение документа

Этот документ описывает методологию обучения для платформы самодостаточных профессиональных тренажеров.

Задача Learning Experience Designer — сделать так, чтобы платформа не превратилась в набор AI-чатов, а действительно тренировала навыки.

Документ фиксирует:

- как человек учится через тренажер;
- как строится trainer product;
- как строится skill map;
- как проектируются сценарии;
- как повышается сложность;
- как работают подсказки;
- как работает повторение;
- как измеряется прогресс;
- как строятся assessment rubrics;
- как дается feedback;
- как отличить хороший тренажер от слабого.

## 1. Главный методологический принцип

Платформа должна тренировать **применение навыка в ситуации**, а не просто проверять знание теории.

Правильная формула тренажера:

```text
контекст
→ задача / ситуация
→ действие пользователя
→ оценка по критериям
→ объяснение
→ повторение
→ рост сложности
→ измеримый прогресс
```

Неправильная формула:

```text
прочитал теорию
→ ответил в свободный AI-чат
→ получил общий комментарий
```

---

## 2. Что такое профессиональный тренажер с точки зрения обучения

Самодостаточный trainer product должен содержать не только сценарии, но и полную учебно-тренировочную логику.

У каждого тренажера должны быть:

```text
целевая аудитория
цель тренировки
карта навыков
уровни сложности
сценарии
рубрики оценки
feedback model
подсказки
механика повторений
правила прогресса
критерии готовности
```

Пример:

```text
Trainer Product: QA Engineer Interview Trainer

Цель:
Подготовить пользователя к реальному QA-собеседованию через практику ответов, разбор ошибок и постепенное улучшение навыков.

Навыки:
- requirements analysis
- test design
- bug reporting
- API testing
- SQL basics
- communication
- interview structure

Метод:
короткие сценарии 5–15 минут
→ ответ пользователя
→ оценка по рубрике
→ рекомендация
→ повторная попытка
```

## 3. Learning Design Framework

### 3.1. Как человек учится в тренажере

Пользователь проходит цикл:

```text
1. Понимает контекст
2. Пробует ответить / решить ситуацию
3. Получает честную оценку
4. Видит конкретную ошибку
5. Получает подсказку или пример
6. Повторяет попытку
7. Видит улучшение
8. Переходит к более сложной ситуации
```

Этот цикл должен быть встроен во все trainer products.

### 3.2. Основной цикл обучения

```text
Attempt
→ Evaluation
→ Feedback
→ Reflection
→ Retry / Next Scenario
→ Progress Update
```

Расшифровка:

| Этап | Что происходит | Зачем |
|---|---|---|
| Attempt | Пользователь выполняет сценарий | Практика вместо пассивного чтения |
| Evaluation | Система оценивает по рубрике | Объективная структура оценки |
| Feedback | Пользователь получает разбор | Понимает, что улучшить |
| Reflection | Пользователь осознает ошибку | Повышается качество следующей попытки |
| Retry / Next | Повторяет или идет дальше | Закрепление |
| Progress | Обновляется skill score | Видна динамика |

## 4. Методологическая структура Trainer Product

Каждый trainer product должен быть построен по одной структуре:

```text
Trainer Product
├── Target Audience
├── Learning Goals
├── Skill Map
├── Tracks
├── Modules
├── Scenarios
├── Rubrics
├── Feedback Rules
├── Progress Rules
└── Readiness Criteria
```

### 4.1. Target Audience

Нужно четко определить, для кого тренажер.

Пример для QA:

```text
Primary audience:
- Junior QA candidates
- Manual QA beginners
- QA students before first interviews

Secondary audience:
- Middle QA refreshing interview basics
- Career switchers entering QA
```

### 4.2. Learning Goals

Learning goals должны быть измеримыми.

Плохо:

```text
Научить проходить собеседование.
```

Хорошо:

```text
Пользователь умеет структурированно отвечать на типовые QA interview questions.
Пользователь умеет объяснить, как оформлять bug report.
Пользователь умеет привести пример test case.
Пользователь умеет объяснить difference between smoke, regression and retest.
```

### 4.3. Tracks

Track — крупная линия тренировки.

Для QA Interview Trainer:

```text
Track 1: HR / self-presentation
Track 2: QA theory basics
Track 3: Test documentation
Track 4: Bug reporting
Track 5: API / SQL basics
Track 6: Practical interview simulation
```

### 4.4. Modules

Module — группа сценариев внутри track.

Пример:

```text
Track: Bug Reporting
├── Module: Bug report structure
├── Module: Severity vs Priority
├── Module: Reproduction steps
└── Module: Communicating bugs in interview
```

### 4.5. Scenario

Scenario — конкретная тренировочная ситуация.

Пример:

```text
Scenario:
Интервьюер просит объяснить, как вы оформляете баг-репорт.
```


### 5.4. Детализация QA Skill Map

| Skill ID | Навык | Что пользователь должен уметь |
|---|---|---|
| interview_structure | Структура ответа | Давать ответ по понятной логике, не прыгать между мыслями |
| communication_clarity | Ясность коммуникации | Объяснять просто, без лишней воды |
| requirements_analysis | Анализ требований | Видеть неполные/неясные требования |

| api_testing | API basics | Понимать request/response/status codes/Postman basics |
| sql_basics | SQL basics | Объяснить SELECT/WHERE/JOIN на базовом уровне |
| qa_terms | QA terminology | Различать smoke, regression, retest, sanity, severity, priority |
| practical_reasoning | Практическая логика | Применять знание к ситуации, а не только давать определение |
| self_presentation | Самопрезентация | Рассказать о себе релевантно роли |
| uncertainty_handling | Работа с незнанием | Честно и спокойно отвечать, если не знает точный ответ |

## 6. Skill Levels

### 6.1. Уровни развития навыка

Для каждого навыка используем 4 уровня:

```text
0. Not observed
1. Basic
2. Developing
3. Ready
4. Strong
```

### 6.2. Описание уровней

| Level | Название | Описание |
|---:|---|---|
| 0 | Not observed | Навык не проявлен или ответ отсутствует |
| 1 | Basic | Есть частичное понимание, но ответ слабый/неструктурный |
| 2 | Developing | Ответ в целом понятен, но есть пробелы |
| 3 | Ready | Ответ достаточен для junior-level собеседования |
| 4 | Strong | Ответ уверенный, структурный, с примером и хорошей логикой |

### 6.3. Readiness Interpretation

```text
0–1: требуется повторение
2: можно продолжать, но навык еще слабый
3: пользователь готов по этому навыку
4: сильная зона
```

## 7. Scenario Design Template

### 7.1. Назначение сценария

Сценарий должен тренировать конкретную ситуацию, а не “спросить что-нибудь”.

### 7.2. Общий шаблон сценария

```json
{
  "scenario_id": "qa_bug_report_explanation_v1",
  "trainer_product": "QA Engineer Interview Trainer",
  "track": "Bug Reporting",
  "module": "Bug Report Structure",
  "title": "Как вы оформляете баг-репорт?",
  "goal": "Проверить, умеет ли пользователь объяснить структуру баг-репорта",
  "target_skills": [
    "bug_reporting",
    "communication_clarity",
    "interview_structure"
  ],
  "difficulty": "junior",
  "estimated_duration_minutes": 8,
  "user_role": "candidate",
  "ai_role": "interviewer",
  "context": "Вы проходите собеседование на позицию Junior QA Engineer.",
  "task": "Ответьте на вопрос интервьюера: как вы оформляете баг-репорт?",
  "expected_actions": [
    "назвать основные поля баг-репорта",
    "объяснить importance of steps to reproduce",
    "упомянуть actual vs expected result",
    "сказать про environment/screenshots/logs when relevant"
  ],
  "common_errors": [
    "перечислить только title и description",
    "не упомянуть steps to reproduce",
    "путать severity and priority",
    "говорить слишком общо"
  ],
  "hints": [
    "Подумайте, что нужно разработчику, чтобы воспроизвести баг.",
    "В хорошем баг-репорте обычно есть expected и actual result.",
    "Можно упомянуть environment, screenshots или logs."
  ],
  "success_criteria": [
    "ответ структурирован",
    "названы ключевые поля",
    "есть объяснение зачем нужны reproduction steps",
    "нет критичных ошибок"
  ],
  "critical_errors": [
    "утверждает, что шаги воспроизведения не нужны",
    "не понимает разницу между expected и actual result"
  ],
  "rubric_id": "qa_bug_report_rubric_v1"
}
```

### 7.3. Обязательные поля сценария

| Поле | Обязательно | Зачем |
|---|---|---|
| goal | Да | Чтобы сценарий имел учебную цель |
| target_skills | Да | Чтобы прогресс был связан с навыками |
| difficulty | Да | Чтобы строить уровни сложности |
| context | Да | Чтобы пользователь понимал ситуацию |
| user_role | Да | Чтобы задать позицию пользователя |
| ai_role | Да | Чтобы AI не выходил из роли |
| expected_actions | Да | Чтобы оценивать не абстрактно |
| common_errors | Да | Чтобы давать полезный feedback |
| hints | Да | Чтобы помогать без готового ответа |
| success_criteria | Да | Чтобы определить PASS |
| critical_errors | Да | Чтобы фиксировать блокирующие ошибки |
| rubric_id | Да | Чтобы оценка была по рубрике |

## 8. Scenario Difficulty Model

### 8.1. Уровни сложности

```text
Level 1 — Guided
Level 2 — Basic
Level 3 — Applied
Level 4 — Mixed
Level 5 — Stress / Realistic
```

### 8.2. Описание уровней

| Level | Название | Описание |
|---:|---|---|
| 1 | Guided | Есть подсказки, контекст простой, один навык |
| 2 | Basic | Типовой вопрос, один основной навык |
| 3 | Applied | Нужно применить знание в ситуации |
| 4 | Mixed | Несколько навыков в одном сценарии |
| 5 | Stress / Realistic | Реалистичная сложная ситуация, уточняющие вопросы, давление времени later |

### 8.3. Пример progression для QA

```text
Level 1:
Что такое bug report?

Level 2:
Как вы оформляете bug report?

Level 3:
Вам дали баг: кнопка Save не работает. Как оформить report?

Level 4:
Пользователь говорит, что иногда данные не сохраняются. Что вы спросите и как проверите?

Level 5:
Интервьюер спорит: “Разработчик и так поймет, зачем steps to reproduce?” Что ответите?
```

## 9. Hint System

### 9.1. Назначение подсказок

Подсказка должна помогать думать, а не сразу давать готовый ответ.

### 9.2. Уровни подсказок

```text
Hint 1 — direction
Hint 2 — structure
Hint 3 — example fragment
```

### 9.3. Пример

Сценарий: “Как вы оформляете bug report?”

```text
Hint 1:
Подумайте, что нужно разработчику, чтобы воспроизвести проблему.

Hint 2:
Хороший ответ может идти по структуре: title → steps → expected result → actual result → environment.

Hint 3:
Например: “Я указываю шаги воспроизведения, потому что без них разработчику сложно проверить проблему.”
```

### 9.4. Когда давать подсказку

```text
пользователь просит hint
пользователь отправил слишком короткий ответ
пользователь провалил предыдущую попытку по тому же критерию
пользователь делает повторную попытку
```

### 9.5. Когда не давать подсказку

```text
до первой попытки, если сценарий не guided
вместо оценки
как готовый полный ответ
если подсказка раскрывает весь смысл сценария
```

## 10. Repetition Model

### 10.1. Почему повторение обязательно

Пользователь учится не от одного feedback, а от повторного применения.

Тренажер должен поддерживать:

```text
retry same scenario
retry with hint
retry after review
next scenario with same skill
mixed scenario later
```

### 10.2. Модель повторения

```text
Fail / weak result
→ show feedback
→ recommend retry
→ provide targeted hint
→ evaluate again
→ compare attempt 1 vs attempt 2
```

### 10.3. Retry Rules

| Ситуация | Рекомендация |
|---|---|
| overall score < 50 | Повторить тот же сценарий |
| critical error present | Повторить после объяснения critical error |
| score 50–69 | Повторить с подсказкой или пройти related scenario |
| score 70–84 | Можно идти дальше, но показать weak point |
| score >= 85 | Рекомендовать следующий уровень |

### 10.4. Spaced Repetition later

Для следующих фаз:

```text
повторить слабый навык через 1 день
повторить через 3 дня
повторить через 7 дней
смешанный сценарий через 14 дней
```

MVP:

```text
manual/algorithmic next recommendation based on last evaluation
```

## 11. Progress Measurement Model

### 11.1. Что измеряем

Нельзя измерять только completion.

Измеряем:

```text
completion
overall score
skill score
score improvement
critical errors
hint usage
retry improvement
scenario difficulty reached
readiness status
```

### 11.2. Progress по trainer product

Прогресс должен быть отдельно для каждого trainer product.

```text
QA Interview Trainer progress ≠ Sales Trainer progress
```

### 11.3. Skill Score Calculation MVP

Простая модель:

```text
skill_score = weighted average of latest N evaluations connected to this skill
```

MVP рекомендуемое N:

```text
N = 3 latest evaluated attempts per skill
```

### 11.4. Readiness Status

```text
not_started
in_progress
needs_practice
almost_ready
ready_for_mock_interview
strong
```

### 11.5. Readiness Rules MVP

```text
not_started:
no completed scenarios

in_progress:
1+ scenario completed, average score < 60

needs_practice:
average score 60–69 or critical errors exist

almost_ready:
average score 70–79, no recent critical errors

ready_for_mock_interview:
average score 80+, required scenarios completed

strong:
average score 90+, strong performance across core skills
```

## 12. Assessment Rubric Template

### 12.1. Назначение рубрики

Рубрика нужна, чтобы AI не оценивал “на глаз”.

Рубрика должна быть:

```text
понятной
измеримой
привязанной к навыкам
одинаковой для похожих сценариев
проверяемой QA и экспертом
```

### 12.2. Общий шаблон рубрики

```json
{
  "rubric_id": "qa_bug_report_rubric_v1",
  "name": "Bug Report Explanation Rubric",
  "scale": "0-5",
  "pass_score": 3,
  "criteria": [
    {
      "criterion_id": "structure",
      "name": "Структура ответа",
      "skill_id": "interview_structure",
      "weight": 0.2,
      "description": "Ответ логичен, последовательный и понятный",
      "levels": {
        "0": "Ответ отсутствует или не по теме",
        "1": "Ответ хаотичный, структура почти отсутствует",
        "2": "Есть базовая логика, но ответ неполный",
        "3": "Ответ достаточно структурирован для junior level",
        "4": "Ответ хорошо структурирован и понятен",
        "5": "Ответ очень ясный, краткий, полный и уверенный"
      },
      "good_answer_example": "Я обычно описываю title, шаги воспроизведения, expected result, actual result, environment и прикладываю скриншоты или логи, если они помогают.",
      "weak_answer_example": "Я просто пишу, что не работает.",
      "critical_errors": []
    }
  ]
}
```

### 12.3. Rubric Criteria для QA Bug Report Scenario

| Criterion | Weight | Skill |
|---|---:|---|
| Structure | 20% | interview_structure |
| Key fields knowledge | 30% | bug_reporting |
| Practical reasoning | 20% | practical_reasoning |
| Communication clarity | 20% | communication_clarity |
| No critical misconceptions | 10% | qa_terms / bug_reporting |

### 12.4. Score Interpretation

| Score | Meaning |
|---:|---|
| 0 | Нет ответа / не по теме |
| 1 | Сильно слабый ответ |
| 2 | Частично верно, но много пробелов |
| 3 | Достаточно для junior-level |
| 4 | Хороший ответ |
| 5 | Очень сильный ответ |

### 12.5. Critical Errors

Critical error — ошибка, которая блокирует PASS, даже если часть ответа хорошая.

Примеры для QA:

```text
говорит, что steps to reproduce не нужны
путает actual и expected result полностью
утверждает, что баг-репорт должен содержать только title
не понимает, зачем указывать environment
```

Правило:

```text
Если есть critical error, scenario cannot be marked as passed.
```

## 13. Feedback Model

### 13.1. Главный принцип feedback

Feedback должен отвечать на 4 вопроса:

```text
Что получилось?
Что не получилось?
Почему это важно?
Что сделать в следующей попытке?
```

### 13.2. Feedback Structure

```text
1. Короткий итог
2. Сильная сторона
3. Главная зона улучшения
4. Evidence из ответа
5. Конкретный следующий шаг
6. Retry / next scenario recommendation
```

### 13.3. Good Feedback Example

```text
Ты дал понятный общий ответ и правильно упомянул шаги воспроизведения.

Что стоит усилить:
сейчас не хватает expected result и actual result. Без них разработчику сложнее понять, в чем именно проблема.

Фрагмент из твоего ответа:
"Я описываю проблему и шаги."

Следующий шаг:
попробуй повторить ответ по структуре:
title → steps to reproduce → expected result → actual result → environment.
```

### 13.4. Bad Feedback Example

```text
Ответ плохой. Нужно лучше знать баг-репорты.
```

Почему плохо:

```text
унижает
не объясняет
нет evidence
нет следующего шага
нет структуры
```

### 13.5. Feedback by Attempt Number

#### First failed attempt

Тон мягкий, поддерживающий.

```text
Ты начал правильно, но ответ можно сделать структурнее.
```

#### Second failed attempt

Больше конкретики.

```text
Ошибка повторяется: ты снова не указал actual result. Это ключевая часть bug report.
```

#### Third failed attempt and later

Нужно предложить learning support.

```text
Похоже, этот элемент пока не закрепился. Перед следующей попыткой посмотри короткую структуру bug report и повтори по шаблону.
```

### 13.6. Feedback by Score

| Score | Feedback Style |
|---:|---|
| 0–29 | Поддержать, объяснить базу, дать guided retry |
| 30–49 | Выделить 1–2 главные ошибки, не перегружать |
| 50–69 | Дать конкретную доработку |
| 70–84 | Похвалить, указать точечное улучшение |
| 85–100 | Подтвердить готовность, предложить следующий уровень |

## 14. Anti-Hallucination Learning Rules

AI feedback must not:

```text
выдумывать, что пользователь сказал
приписывать пользователю знания, которых не было в ответе
давать score без evidence
давать generic advice
менять критерии оценки на лету
оценивать вне рубрики
делать медицинские/юридические утверждения без expert rules
```

AI feedback must:

```text
ссылаться на ответ пользователя
объяснять оценку через rubric criteria
давать конкретный next step
сохранять спокойный тон
```

## 15. Learning Quality Gates

### 15.1. Scenario Quality Gate

Сценарий нельзя публиковать, если:

```text
нет цели
нет target skills
нет difficulty
нет expected actions
нет common errors
нет hints
нет rubric
нет success criteria
нет critical error rules
```

### 15.2. Rubric Quality Gate

Рубрику нельзя использовать, если:

```text
критерии слишком общие
нет описания уровней 0–5
нет связи с skill map
нет examples
нет critical errors
нет pass logic
```

### 15.3. Feedback Quality Gate

Feedback не проходит quality gate, если:

```text
нет конкретики
нет evidence
есть унижение
нет следующего шага
слишком много текста
есть противоречие между score и feedback
```

### 15.4. Trainer Product Learning Gate

Trainer product не считается самодостаточным, если:

```text
нет skill map
нет progression model
нет минимум 3–5 сценариев в MVP
нет rubric pack
нет progress rules
нет readiness logic
```

## 16. Learning Design for QA Engineer Interview Trainer MVP

### 16.1. MVP Learning Goal

Пользователь должен потренироваться отвечать на типовые вопросы Junior QA interview и получить оценку по структуре, ясности и предметной корректности.

### 16.2. MVP Scenario Set

Minimum viable scenario pack:

```text
1. Расскажите о себе как о QA candidate
2. Что такое тест-кейс и чеклист?
3. Как вы оформляете bug report?
4. Чем regression testing отличается от retest?
5. Как бы вы протестировали login form?
```

### 16.3. MVP Skill Coverage

| Scenario | Main Skill | Secondary Skills |
|---|---|---|
| Tell about yourself | self_presentation | communication, interview_structure |
| Test case vs checklist | test_documentation | qa_terms, clarity |
| Bug report | bug_reporting | structure, practical_reasoning |
| Regression vs retest | qa_terms | clarity |
| Login form testing | test_design | requirements_analysis, practical_reasoning |

### 16.4. MVP Progress Logic

```text
Complete 5 scenarios
→ average score calculated
→ weak skills identified
→ readiness status assigned
→ next recommendation generated
```

### 16.5. MVP Readiness Output

```text
"Сейчас ты почти готов к базовому QA interview, но стоит усилить bug reporting и test design."
```

## 21. Edge Cases in Learning Design

| Edge Case | Required Behavior |
|---|---|
| Пользователь дал пустой ответ | Не отправлять на AI evaluation, попросить написать ответ |
| Ответ слишком короткий | Дать controlled feedback или hint |
| Ответ не по теме | Оценить низко, объяснить, что именно не связано с задачей |
| Пользователь просит готовый ответ | Дать структуру, но не заменять тренировку |
| Пользователь провалил 3 раза | Предложить guided mode или review |
| AI feedback слишком общий | Блокировать через quality gate |
| Есть critical error | Не ставить PASS |
| Сильный ответ, но плохая структура | Показать, что знания есть, но надо улучшить подачу |
| Хорошая структура, но неправильная теория | Оценить теорию как слабую, не завышать score |

## 22. Methodology Acceptance Criteria

### 22.1. Skill Map

```gherkin
Given a trainer product is created
When Learning Designer reviews it
Then it must contain a skill map with measurable skills
```

### 22.2. Scenario

```gherkin
Given a scenario is created
When it is validated
Then it must include goal, context, target skills, expected actions, common errors, hints, rubric and success criteria
```

### 22.3. Rubric

```gherkin
Given a scenario has a rubric
When an answer is evaluated
Then each criterion must produce score, evidence, feedback and improvement advice
```

### 22.4. Feedback

```gherkin
Given a user receives feedback
When the result page is shown
Then feedback must include strengths, weak points, evidence and next action
```

### 22.5. Progress

```gherkin
Given a user completes multiple attempts
When progress is recalculated
Then skill scores must update only for skills connected to evaluated scenarios
```

### 22.6. Critical Error

```gherkin
Given an answer contains a critical error
When evaluation is generated
Then the scenario cannot be marked as passed
```

## 25. Risks

| Risk | Severity | Mitigation |
|---|---:|---|
| Тренажер станет обычным AI-чатом | High | Scenario + rubric + skill map required |
| Feedback будет общим | High | Evidence and next action required |
| AI будет завышать оценки | High | Rubric levels + critical errors + test set |
| Пользователь не поймет прогресс | Medium | Skill scores and readiness labels |
| Сценарии будут слишком сложными | Medium | Difficulty model and guided scenarios |
| Повторение будет скучным | Medium | Retry comparison and targeted hints |
| Медицина/право дадут опасные советы | High | Expert review and domain safety gates |

## 28. Final Notes

Главная защита качества:

```text
Каждый сценарий должен тренировать конкретный навык.
Каждая оценка должна быть по рубрике.
Каждый feedback должен давать следующий шаг.
Каждый прогресс должен быть связан с skill map.
```

Если эти правила соблюдены, платформа будет не просто “разговаривать с пользователем”, а действительно тренировать профессиональные навыки.
